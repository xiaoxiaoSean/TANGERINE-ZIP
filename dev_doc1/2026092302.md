## 二、窗口迁移与布局

项目目标是 .NET 10 Windows WPF，而不是以 WinForms 窗体承载界面。项目文件 TANGERINE-ZIP/TANGERINE-ZIP.csproj 使用 net10.0-windows、UseWPF=true，保留 Windows x64 自包含单文件发布配置。窗口由独立 XAML 和对应的 XAML 代码文件组成，Visual Studio 可以按普通 WPF 项目识别窗口及其布局。

本轮界面涉及八个窗口：

| 当前 WPF 窗口 | 用途 | 旧名称 |

## 四、ResX 损坏反馈及修复

用户随后指出 .resx 损坏。问题源于一次过度清理：助手把六份 UiStrings*.resx 重写成仅包含数据和少量 resheader 的精简 XML。该结构能通过当时的 dotnet 编译，但缺少 Visual Studio 常见的完整 ResX schema 和 reader/writer 头，不适合按正常 Visual Studio 资源文件处理。仅凭编译成功就宣称资源文件可供设计器使用，是此前判断不足。

修复时从迁移前提交 120a11b 的 LanguageResource*.resx 取回标准 ResX 文件头，包括 schema、resmimetype、version、reader 和 writer，接到当前 UiStrings*.resx 的资源数据之前。没有回退已更名的资源键，也没有重译文字。六个文件每个都有 182 条数据；修复时逐项比较旧文件与新文件的键和值，除上述三个有意改名的键外，资源值保持一致。随后使用 System.Resources.ResXResourceReader 逐一读取六个文件，均取得 182 条资源，项目构建通过。

标准 ResX 头中会出现 System.Windows.Forms 的 ResXResourceReader/ResXResourceWriter 类型名。这是 ResX 文件格式元数据，不是应用窗口重新使用 WinForms。为保障 Visual Studio 资源编辑器兼容性，保留了这部分标准头，而窗口实现仍为 WPF。对话中没有在 Visual Studio 图形资源编辑器里逐个打开六个文件的直接检查记录。

修复资源时还发现 MainWindow.xaml.cs 有两个同名 MainWindow_Loaded 方法，其中一个是空的 RoutedEventArgs 重载，XAML 可能绑定空方法，使主窗口启动初始化不执行。已删除空重载，把实际初始化方法改为 RoutedEventArgs 签名；当时的 UI 检查再次通过。

## 九、主窗口初始长宽比例

用户随后提出：“我希望主窗口启动时的大小的长宽比是1:根号2 然后更新md”。由于这句话可能表示竖向或横向，助手询问了“宽:高=1:√2（竖向）”与“高:宽=1:√2（横向）”的区别。用户澄清：“说错了，长根号2，宽1，这样的比例，至于多少px自动设置”。最终按主窗口横向展示处理，即长边为水平宽度，宽:高=√2:1。
